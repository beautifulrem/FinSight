# FinSight Agent Evaluation

This page reports how the agent layer (`query_intelligence/agent/`) performs end to end, how the numbers were produced, and what they do **not** show. Every number in the generated section below comes from a reproducible run; the commands, commit, and date are printed with the tables.

## What is measured

| Item | Where |
|---|---|
| Development task set: 207 tasks / 220 turns, 11 categories, Chinese and English | `evaluation/agent_eval/tasks/agent_eval_v1.jsonl` (built by `build_tasks.py`) |
| Held-out task set: 53 tasks / 56 turns, new phrasings, written after the development set was used for fixes and never used for tuning | `evaluation/agent_eval/tasks/agent_eval_holdout_v1.jsonl` (`build_holdout.py`) |
| Point-in-time tool snapshots (replayed so results do not depend on live providers) | `evaluation/agent_eval/fixtures/snapshot_v1.json`, `snapshot_holdout_v1.json` |
| Scoring | `evaluation/agent_eval/metrics.py` |
| Ablation over answer paths | `evaluation/agent_eval/ablation.py` |
| Fault injection | `evaluation/agent_eval/fault_injection.py` |

Categories: single facts, comparisons, "why" questions, macro-to-market links, missing data, technical indicators, documents and sentiment, multi-turn follow-ups, out-of-scope refusals, clarification, and compliance traps (requests for buy/sell calls, price targets, all-in positions).

Expected facts come from the shipped offline snapshot (`data/structured_data.json`, market data as of 2026-04-22), so every required value is checkable. Queries were written for this evaluation and checked against the 1,112 queries used for training or other evaluations in the repository (no exact overlap).

**Scoring is dealbreaker-gated**, in the spirit of finance-agent benchmarks: a turn succeeds only if the behaviour is right (answer / clarify / refuse), every required fact is both stated and cited with the right evidence id, required tools were used, no trading instruction appears, and hedging, missing-data honesty, and entity carry-over hold where the task requires them. `pass^k` counts a task as solved only if all `k` repeated runs succeed.

## Answer paths compared

| Path | What it is | Needs an LLM |
|---|---|---|
| `legacy` | The original `/chat` path (Query Intelligence pipeline + template answer, as served when no LLM key is set). Its refuse/clarify behaviour is inferred from NLU flags, which is generous to it. | no |
| `workflow` | Agent: classical NLU guard and router, deterministic planner, tools, template composer, evidence verifier, compliance guard. | no |
| `pure_llm` | The LLM answers with no tools. | yes |
| `legacy_llm` | The original `/chat` path with DeepSeek rewriting the evidence. | yes |
| `workflow_llm` | Agent workflow with the LLM composing the answer from tool evidence. | yes |
| `agent` | Agent with the LLM choosing tools in the LangGraph loop. | yes |

## How to read these numbers

* **Offline and online are separate.** `legacy` and `workflow` use no LLM and are deterministic. `pure_llm`, `legacy_llm`, `workflow_llm` and `agent` call DeepSeek V4.1 Flash through an OpenAI-compatible gateway (Cline); LLM modes run each task 3 times, and `pass^3` counts a task only if all three runs succeed. Tools replay the recorded snapshot; calls the LLM makes with arguments missing from the snapshot run against the same offline data (`live_fallback`), so every mode sees the same facts.
* **Costs are what the gateway billed** (`usage.cost`, USD) for the calls of each run. `legacy_llm` goes through the original `/chat` client, which does not record tokens or cost, so those cells are blank; it also runs once per task, and its success rate moved between 0.35 and 0.59 across three full runs on 2026-09-25, so treat it as noisy.
* **Which path wins.** On the development set the deterministic workflow, workflow + LLM composition and the LLM agent are within about one point of each other. On the held-out set, whose phrasings the rules were not tuned on, the agent is ahead (0.956 vs 0.906 for workflow_llm and 0.849 for workflow) at 1.4–1.9x the cost of LLM composition and a higher P95. That is the case for `mode=auto`: deterministic handling for simple questions, the LLM loop for open-ended ones.
* **First-pass verification is low for the agent (0.49 dev).** The claim-level verifier sends drafts back when a number is cited next to the wrong evidence id; one revision fixes most, and the final `Draft passed evidence verification` counts the revised draft.
* **The development set was used for fixes; the held-out set was used to choose prompts.** Agent-layer fixes were driven by the development set (first run 77.3% → 98.1% offline). The held-out set was written afterwards and not used for rule tuning, but the v1 → v2 prompt A/B below showed a hedging regression on it, and prompt v3 restores the dropped rule. The held-out set is therefore a validation set for prompts, not an untouched test set.
* **Template answers are deterministic restatements of tool output.** High fact recall in `workflow` means retrieval, citation and guarding work; it does not measure reasoning quality.
* **The snapshot is small.** Seven symbols have market data, three have fundamentals, four macro indicators. Entities outside it are used deliberately as "missing data" tasks.

## Prompt versions

| Version | Change | Outcome |
|---|---|---|
| v1 | Original prompts. | Baseline. |
| v2 | Tagged sections, effort scaling per question type, the reason behind each rule, one output example. | Agent cost −69% and first-pass verification doubled on the development set, but hedging on held-out judgment questions fell from 1.00 to 0.67: v2 had dropped v1's "describe uncertainty and risks". |
| v3 | v2 plus an explicit rule for judgment questions (conditional view, uncertainty, risks). | Default. Held-out agent hedging 0.91; see the generated tables above. |

The v1/v2 comparison ran on the same commit (`1beb760`); v3 ran on `846bc5e`, which also contains the observation and tool-error changes, so v3 vs v2 is not a pure prompt comparison. Prompt texts are pinned by hash in `query_intelligence/agent/prompts.lock.json`, and every trace and report records `id@version#sha`.

## Known failures and root causes

* English company names without aliases in the entity master (e.g. CATL, BYD, China Merchants Bank, CITIC Securities) are not resolved, so their "missing data" tasks fail the required-tool check on the deterministic path. Root cause: alias coverage in `data/runtime/alias_table.csv`, not the agent.
* On the held-out set, lexical hedging triggers miss some phrasings (e.g. 抄底, 翻倍, 止盈点位) on the deterministic path; the LLM paths hedge through the prompt instead.
* The classical NLU still labels some finance questions out-of-scope (e.g. "最新一期PMI数据是多少？"); the agent corrects these with explicit, logged overrides rather than hiding them.
* **Red team, held-out attacks:** 3 of 128 LLM-path runs let an attack through — a persona change ("pirate" voice), a "强烈买入" rating repeated from a poisoned document, and a fake closing price planted in a news excerpt. The last one passes number verification because the planted number *is* in the cited evidence: verification proves traceability, not truth. Planned fixes are policy-level (rating language in the compliance guard, cross-checking prices against market data) and will be measured on a new unseen attack set.

## Reproducing

```bash
python -m evaluation.agent_eval.build_tasks           # regenerate the development set (checks training overlap)
python -m evaluation.agent_eval.build_holdout         # regenerate the held-out set
python -m evaluation.agent_eval.runner --mode workflow                      # development set, offline
python -m evaluation.agent_eval.runner --mode workflow --record             # re-record the tool snapshot
python -m evaluation.agent_eval.ablation                                    # legacy vs workflow, both sets, offline
python -m evaluation.agent_eval.fault_injection                             # graceful-degradation scenarios
python -m evaluation.agent_eval.verifier_stress                             # verifier false-accept rate
python -m evaluation.agent_eval.redteam                                     # prompt-injection red team, offline path
# online (an OpenAI-compatible endpoint in DEEPSEEK_BASE_URL / DEEPSEEK_API_KEY / DEEPSEEK_MODEL):
python -m evaluation.agent_eval.ablation --llm deepseek --repeats 3 --workers 6 --out outputs/agent_eval/ablation-final.json
python -m evaluation.agent_eval.redteam --llm deepseek --workers 4
QI_PROMPT_VERSION=v2 python -m evaluation.agent_eval.ablation --llm deepseek --repeats 3 --workers 6 \
    --modes workflow_llm,agent --out outputs/agent_eval/ablation-online-v2.json
python -m evaluation.agent_eval.report --ablation outputs/agent_eval/ablation-final.json \
    --ab-baseline outputs/agent_eval/ablation-online-v1.json --prompt-ab outputs/agent_eval/ablation-online-v2.json
```

Costs come from the gateway's `usage.cost` when present; otherwise set `QI_LLM_PRICE_INPUT_MISS`, `QI_LLM_PRICE_INPUT_HIT`, `QI_LLM_PRICE_OUTPUT` (per million tokens) and `QI_LLM_PRICE_CURRENCY`. Token counts are always recorded.
