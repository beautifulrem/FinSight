# FinSight Agent 化：设计复盘

本文记录 Agent 层的关键设计决策、取舍、实际遇到的失败案例、消融结论和已知局限，可直接用于项目汇报或面试讲解。所有数字都出自 [Agent 评测报告](../agent-eval.md)、[性能](../performance.md) 与 [部署](../deployment.md) 文档，那里给出了命令、commit 与日期。在线结果只来自一个模型（DeepSeek V4.1 Flash，经网关调用），每个任务重复 3 次。

## 1. 一句话定位

**证据优先的金融研究 Agent**：由经典、可解释的 NLU 负责理解、守卫和路由；Agent 把行情、基本面、宏观、文档检索、情感这些已有能力封装为 9 个类型化工具，按确定性计划或由 LLM 调用。每个回答都要经过「引用存在 + 数字可追溯」校验和金融合规处理，没有 LLM 时也能完整运行。

与原系统的区别：原 `/chat` 固定执行「NLU → 检索 → 一次 LLM 改写」，不会追加取数、不会追问，也不检查 LLM 写出的数字。现在每一轮都可以决定调用哪些工具、缺标的时暂停并追问、在答案出现无证据数字时要求修改或删除该子句，并且全过程可追踪。

## 2. 关键设计决策与取舍

| 决策 | 选择 | 放弃了什么 / 为什么 |
|---|---|---|
| 总体架构 | **混合式**：经典 NLU 做守卫/路由，简单问题走确定性 workflow，复杂问题才交给 LLM 工具循环（`mode=auto`） | 放弃「全部交给 LLM」。依据 Anthropic 的建议：能用 workflow 解决就不用 agent。金融问答中大部分是单点查询，确定性路径更便宜、可复现、可离线测试。代价是需要维护路由规则，路由原因全部写入 `route_reasons` 以便排查。 |
| 编排框架 | LangGraph `StateGraph` | 需要的三项能力它都原生提供：checkpointer（会话记忆）、`interrupt()`（澄清后恢复）、条件边（校验失败后修改）。代价是状态 reducer 需要谨慎设计（见 §3 的状态泄漏案例）。 |
| 不做多 Agent 角色扮演 | 单图 + 「规划 / 校验」两个职责 | 分析师/交易员式的多角色辩论（TradingAgents 类）会让成本和不可控性成倍增加，而本项目的价值在于证据链。校验是确定性代码，不是另一个 LLM。 |
| 检索主干 | 保持 PostgreSQL 全文检索 + TF-IDF + LTR，不引入向量检索 | 这是 AGENTS.md 的约束，也是项目的差异化点：排序特征可解释。Agent 只是复用检索逻辑（`RetrievalPipeline.retrieve_documents`），不重新实现。 |
| LLM 接入 | DeepSeek OpenAI 兼容的 tool calling，**非 strict** 模式；参数统一经过 Pydantic 校验 | strict 模式对 schema 限制较多，且与已配置模型的兼容性无法在离线环境验证。改由 `ToolRegistry` 负责修复 JSON、校验参数，出错时返回 `invalid_arguments` 让模型自行修正。thinking 模式下会回传 `reasoning_content`，否则多轮工具调用会报错。 |
| 事实来源 | 每个工具结果都转成带稳定 `evidence_id` 的 `AgentEvidence`，答案只能引用这些 id | 这样「引用是否存在」和「数字能否在证据中找到」都可以机械检查，不必依赖 LLM 自评。 |
| 幻觉处理 | 校验失败 → 带反馈修改一次 → 仍失败则**按子句**删除无证据内容，并标记 `verification_failed:repaired` | 最初是整句删除，会把正确的内容一起删掉（见 §3）。不选择直接拒答，因为大部分内容通常是对的。 |
| 合规放在最后一个节点 | 软化判断/归因措辞、删除交易指令、补充数据新鲜度提示与免责声明 | 无论答案由 LLM 还是模板生成，都要经过同一道关口；规则复用 `scripts/llm_response.py`，避免两套口径。 |
| 澄清 | 缺标的时 `interrupt()`，由 `/agent/resume` 恢复；每轮最多一次 | 不让 LLM 去猜用户指的是哪只股票。限制一次是为了避免反复追问的死循环。 |
| 降级 | 无 Key、LLM 故障、预算或截止时间耗尽时，由确定性规划器 + 模板完成回答，并在 `degraded` 中说明 | 可用性优先于回答质量；原因必须对用户可见。 |
| 工具输出视为不可信 | 以不可信数据信封包装，证据入库时脱敏指令类文本 | 新闻、公告正文可能包含提示注入。在入库时统一处理，比在每条下游路径分别处理更可靠（见 §3）。 |
| MCP | 使用低层 `Server` 直接发布 Pydantic schema | SDK 2.x 的高层 API 会根据函数签名重新推导 schema，与 ToolRegistry 的 schema 不一致；低层 API 保证两边使用同一份定义。 |
| 可观测性 | JSON trace 落盘 + OTLP 导出 | Langfuse SDK 各大版本的 API 差异大，而 Langfuse、Jaeger、Tempo 都支持 OTLP，走标准协议更稳妥。 |
| 评测 | 回放工具快照、关键事实错误一票否决、dev/holdout 分离、故障注入 | 数据源变化和网络状况不应影响结果；「大致正确」对金融场景没有意义；holdout 用来估计 dev 上的修复有多少能泛化。 |

## 3. 失败案例分析

这些问题都是在实现和评测过程中实际遇到的，每个都附带根因和修复方法。

1. **运行时别名表把表头当成了别名。** `alias_table.csv` 中有一行把「公司名称」登记为春秋电子的别名，于是任何包含这四个字的问题都会被解析为 603890.SH。根因是资产生成脚本没有过滤表头文本。修复：删除该行，并在生成器中屏蔽表头类别名。**启示**：Agent 工具的质量上限取决于底层数据资产。

2. **live provider 默认开启，离线测试逐个等待网络超时。** 基线全量测试需要 49.5 分钟。修复：增加 `offline_service` 测试夹具，CI 显式关闭 live 数据；Agent 工具在 provider 返回告警时不写入缓存。

3. **同一会话中上一轮的证据泄漏到下一轮。** 使用 checkpointer 后，`add` 类型的 reducer 会把上一轮的工具日志和证据累加进来，模型可能引用上一轮的数据。修复：实现可重置的 reducer（`{__reset__}` 标记），每轮开始时显式清空本轮字段，并用测试覆盖。

4. **「那它的市净率呢」查不到公司。** 真实 NLU 只识别出「市净率」这个指标实体，因此不会回退到对话上下文。修复：基于规则的指代改写（它/it/its → 上一轮唯一的上市实体），改写原因写入 `route_reasons`；有歧义或没有候选时发起澄清，不做猜测。

5. **NLU 把宏观问题判成 out-of-scope。** 例如「最新一期PMI数据是多少？」。Agent 层没有重新训练分类器，而是增加了显式、带日志的金融/宏观锚词覆盖规则。问题本身在评测报告中如实保留。

6. **技术指标工具在历史数据不足时返回「成功 + 空值」。** 模板于是写出「MA20 为 —」这类内容。修复：一个指标都算不出来时返回 `unavailable`；部分能算时列出无法计算的指标，答案中明确说明。

7. **提示注入文本出现在答案里。** 故障注入发现 LLM 路径做了脱敏，但模板组答路径直接读取了原始证据。修复：改为证据入库时统一脱敏，所有下游路径看到的都是同一份干净数据。

8. **修复逻辑删掉了正确内容。** 一句话中只要有一个数字没有证据支撑，整句都会被删除。修复：按子句拆分，只删除不被支撑的子句。

9. **评测集的期望值写错了。** 510300 的 MA5 期望值最初是手写的，与数据不符。修复：期望值一律由离线数据推导（`_offline_ma5()`）。**启示**：评测集本身也需要测试。

10. **容器构建失败。** `numpy<2` 在 3.13-slim 上没有可用 wheel，沙箱又无法访问 apt 源。修复：多阶段构建，在完整的 python:3.13 镜像中编译 wheel，运行镜像保持 slim 且不带编译器；同时发现 `mcp` 要求 `pydantic>=2.12`，于是放宽了原来的版本上限。

11. **网关把响应包了一层。** 接入 OpenAI 兼容网关（Cline）后所有 LLM 调用都报 "missing choices"：网关返回 `{"success": true, "data": {...}}`。修复：`unwrap_completion` 同时接受两种形状，并顺带读取网关上报的单次费用 `usage.cost`，成本从此是账单口径而不是估算。

12. **并发首次初始化 V8 直接让进程崩溃。** 在 Chrome 里实测时服务进程被 `Check failed: !pool->IsInitialized()` 杀掉：akshare 的新浪/巨潮解码依赖 `py_mini_racer`（内嵌 V8），Agent 并行调用工具时两个线程同时初始化 V8。数据源审计是串行跑的，所以没暴露。修复：进程内加锁、只初始化一次，回归测试用 8 个线程在子进程里复现。**启示**：并发缺陷只有在真实使用形态下才会出现。

13. **校验器会放过「换了公司的数字」。** 压力测试把 157 个正确答案里的数字改错或互换，原校验器（数字在本轮任何证据里出现即可、13 种倍数、±0.5%）放过了 35%，把 A 公司的 PE 写在 B 公司引用后面时 100% 放过。修复：按句子绑定引用、按单位限定倍数、按写出的精度定容差，误放率降到 2.8%（互换 0.6%），正确答案仍 100% 通过。修改过程中英文模板因「hundred million」单位缺失被误伤，首轮通过率一度降到 0.94，补齐单位表后恢复 1.0。

14. **模板路径把注入文本当标题原样输出。** 红队把攻击语句拆到文档标题里，模板渲染标题时读的是未脱敏的工具日志。修复：工具日志同样脱敏。同时发现关键词过滤器对全角、零宽字符完全失效，改为先做 NFKC 规范化再匹配。**如实记录**：规则是照着 dev 攻击集调的，事后另写的 holdout 攻击集拦截率为 0，防御主要靠结构（只读工具、不可信数据信封、数字校验、合规节点）。

15. **v2 Prompt 省钱但丢了限定语。** 结构化重写（标签分区、按问题类型控制调用次数、规则写理由）让 Agent 单任务成本下降约 69%、首轮校验通过率翻倍，但 holdout 上「判断类问题需要限定语」从 1.00 掉到 0.67。对比发现 v2 删掉了 v1 的「描述不确定性与风险」。v3 补回这条规则。**如实记录**：这个修正是看了 holdout 才做的，因此 holdout 此后是 Prompt 的验证集，不再是未触碰的测试集。

16. **检查点写爆 SQLite。** 容器压测单用户只有 0.73 次/秒、P95 4.6 秒，单次请求却只要 40 ms；会话库 800 次请求后 65 MB。LangGraph 默认每个节点写一次完整状态（每轮约 11 次）。修复：`durability="exit"` + 收尾时清掉大字段，单用户 8.36 次/秒、P95 0.66 秒，库 9 MB。代价：运行中途崩溃会丢这一轮。

17. **只读根文件系统下 Pod 起不来。** K8s 清单开启 `readOnlyRootFilesystem` 后 CrashLoop：efinance 在 import 时往 site-packages 里建目录。修复：镜像里把该目录软链到 `/tmp`（emptyDir），provider 先建好目标目录。

18. **评测报告记错了 commit。** 长时间在线评测结束时才读取 commit，期间的新提交被记成了这次评测的来源。修复：启动时记录 commit，工作区有改动时加 `-dirty` 后缀。

## 4. 消融结论

提交 `846bc5e`，DeepSeek V4.1 Flash（经网关），LLM 路径每任务 3 次；数字取自 `docs/agent-eval.md`。

| 路径 | 开发集成功率 | 保留集成功率 | pass^3（开发/保留） | 单任务成本（开发/保留） | P95（开发） |
|---|---|---|---|---|---|
| 原 `/chat` 无 LLM | 0.256 | 0.189 | – | – | 1.0 s |
| 原 `/chat` + LLM | 0.440 | 0.679 | – | 未记录 | 13.4 s |
| 纯 LLM | 0.000 | 0.000 | 0 / 0 | $0.0009 | 18.3 s |
| 固定流程（无 LLM） | 0.981 | 0.849 | – | 0 | 0.8 s |
| 固定流程 + LLM 组答 | 0.979 | 0.906 | 0.976 / 0.906 | $0.0008 / $0.0007 | 16.7 s |
| LLM Agent | 0.986 | 0.956 | 0.971 / 0.906 | $0.0016 / $0.0010 | 25.2 s |

能得出的结论：

- **工具 + 校验是前提**：纯 LLM 一题都过不了（不能引用证据、价格无法核实），原 `/chat` 加 LLM 改写也只有 0.44/0.68。
- **开发集上三条「有工具」的路径几乎打平**，因为开发集驱动了规则修复；**差距出现在保留集**：Agent 0.956 > 固定流程 + LLM 0.906 > 固定流程 0.849。这正是 `mode=auto` 的依据：简单问题走零 token 路径，开放式问题交给 LLM 循环。
- **代价**：Agent 单任务成本是 LLM 组答的 1.4–1.9 倍，P95 延迟 20–25 秒；Agent 的草稿首轮校验通过率只有 0.49（开发集），靠一次修订兜住。
- **Prompt 迭代有数据支撑**：v1 → v2 同一 commit A/B，Agent 成本 −69%、首轮通过率翻倍，但保留集限定语 1.00 → 0.67；v3 补回规则后限定语 0.91，保留集 pass^3 0.906（v1 为 0.849），成本比 v1 低 60%。

不能得出的结论：

- 只测了一个模型族，结论不一定迁移到其他模型。
- 保留集参与了 Prompt 选择；需要新的、未触碰的测试集来重新估计泛化。
- 模板答案是对工具输出的确定性复述，固定流程的高事实召回不代表推理能力。

## 5. 已知局限

- 在线评测只覆盖一个模型族（DeepSeek V4.1 Flash）；holdout 参与了 Prompt 版本选择。
- 数值校验按句子绑定引用，但同一条证据包含多个报告期或指标时，无法判断选对了哪一个。
- 限定语与指代消解基于规则；英文实体别名覆盖不足（CATL、BYD 等），根因在别名资产。
- 关键词注入过滤器不泛化（holdout 攻击拦截率 0）；安全性主要依赖结构。
- 免费数据源会限流：审计时东方财富拒绝了本机连接，由降级链兜底。
- 单进程约 6–7 次/秒（离线 workflow）；多副本需要 Postgres 检查点，A2A 任务表与 trace 缓冲仍是每个 Pod 各自一份。

## 6. 常见问题（面试视角）

**为什么不全部交给 LLM？** 金融问答大部分是单点查询。确定性路径零 token、可复现、便于解释；在线消融里它在 dev 上与 LLM 路径接近，差距主要出现在 holdout 的开放式问题上，所以路由把复杂问题交给 LLM。

**幻觉率怎么定义、怎么量化？** 两层：线上是「答案中无法由所引证据支撑的数字」，由代码逐句检查并修订/删除；校验器自身的可靠性用压力测试量化——对正确答案注入错误后的误放率，从 35.0% 降到 2.8%，正确答案 100% 通过。

**如何评测一个 Agent？** 回放快照保证可复现；关键事实错误一票否决；dev/holdout 分离；真实 LLM 每任务 3 次算 pass^3；消融对比纯 LLM、固定流程、Agent；Prompt 做 A/B；红队与故障注入测鲁棒性；每个数字附命令与 commit。

**成本和延迟怎么控制？** 路由分流到零 token 路径；按节点设推理强度（组答与修订用 low）；强制收尾和修订保留同一份工具定义并 `tool_choice="none"`，维持缓存前缀；工具结果只按引用列出证据（体积减 36%）；Prompt v2/v3 按问题类型限定调用次数。账单口径的单任务成本见评测报告。

**如何防御提示注入？** 结构优先：工具只读、结果包在不可信数据信封里、数字必须来自证据、合规节点删除交易指令；关键词过滤只是纵深防御，并且我们用 holdout 攻击集证明了它不泛化。

**LLM 或数据源挂了会怎样？** 模型层有容灾链和熔断；图层降级到规划器 + 模板；数据源层按「主源 → 备源 → 缓存 → 快照」降级，并在证据上标注来源与降级原因。

**多轮与人机协作？** LangGraph checkpointer 保存会话；缺标的时 `interrupt()` 暂停，用户回复后从断点恢复并把回复合并进原问题；Postgres 检查点让任意副本都能接着对话（已在 k3s 上验证）。
