# FinSight Agent 化：设计复盘

本文记录 Agent 层的关键设计决策、取舍、实际遇到的失败案例、消融结论和已知局限，可直接用于项目汇报或面试讲解。所有数字都出自 [Agent 评测报告](../agent-eval.md)，那里给出了命令、commit 与日期；没有在线 LLM 的结果，本文也不做相关声称。

## 1. 一句话定位

**证据优先的金融研究 Agent**：由经典、可解释的 NLU 负责理解、守卫和路由；Agent 把行情、基本面、宏观、文档检索、情感这些已有能力封装为 9 个类型化工具，按确定性计划或由 LLM 调用。每个回答都要经过「引用存在 + 数字可追溯」校验和金融合规处理，没有 LLM 时也能完整运行。

与原系统的区别：原 `/chat` 固定执行「NLU → 检索 → 一次 LLM 改写」，不会追加取数、不会追问，也不检查 LLM 写出的数字。现在每一轮都可以决定调用哪些工具、缺标的时暂停并追问、在答案出现无证据数字时要求修改或删除该子句，并且全过程可追踪。

## 2. 关键设计决策与取舍

| 决策 | 选择 | 放弃了什么 / 为什么 |
|---|---|---|
| 总体架构 | **混合式**：经典 NLU 做守卫/路由，简单问题走确定性 workflow，复杂问题才交给 LLM 工具循环（`mode=auto`） | 放弃「全部交给 LLM」。依据 Anthropic 的建议：能用 workflow 解决就不用 agent。金融问答中大部分是单点查询，确定性路径更便宜、可复现、可离线测试。代价是需要维护路由规则，路由原因全部写入 `route_reasons` 以便排查。 |
| 编排框架 | LangGraph `StateGraph` | 需要的三项能力它都原生提供：checkpointer（会话记忆）、`interrupt()`（澄清后恢复）、条件边（校验失败后修改）。代价是状态 reducer 需要谨慎设计（见 §3 的状态泄漏案例）。 |
| 不做多 Agent 角色扮演 | 单图 + 「规划 / 校验」两个职责 | 分析师/交易员式的多角色辩论（TradingAgents 类）会让成本和不可控性成倍增加，而本项目的价值在于证据链。校验是确定性代码，不是另一个 LLM。 |
| 检索主干 | 保持 PostgreSQL 全文检索 + TF-IDF + LTR，不引入向量检索 | 这是 AGENTS.md 的约束，也是项目的差异化点：排序特征可解释。Agent 只是复用检索逻辑（`RetrievalPipeline.retrieve_documents`），不重新实现。 |
| LLM 接入 | DeepSeek OpenAI 兼容的 tool calling，**非 strict** 模式；参数统一经过 Pydantic 校验 | strict 模式对 schema 限制较多，且与已配置模型的兼容性无法在离线环境验证。改由 `ToolRegistry` 负责修复 JSON、校验参数，出错时返回 `invalid_arguments` 让模型自行修正。thinking 模式下会回传 `reasoning_content`，否则多轮工具调用会报错。 |
| 事实来源 | 每个工具结果都转成带稳定 `evidence_id` 的 `AgentEvidence`，答案只能引用这些 id | 这样「引用是否存在」和「数字能否在证据中找到」都可以机械检查，不必依赖 LLM 自评。 |
| 幻觉处理 | 校验失败 → 带反馈修改一次 → 仍失败则**按子句**删除无证据内容，并标记 `verification_failed:repaired` | 最初是整句删除，会把正确的内容一起删掉（见 §3）。不选择直接拒答，因为大部分内容通常是对的。 |
| 合规放在最后一个节点 | 软化判断/归因措辞、删除交易指令、补充数据新鲜度提示与免责声明 | 无论答案由 LLM 还是模板生成，都要经过同一道关口；规则复用 `scripts/llm_response.py`，避免两套口径。 |
| 澄清 | 缺标的时 `interrupt()`，由 `/agent/resume` 恢复；每轮最多一次 | 不让 LLM 去猜用户指的是哪只股票。限制一次是为了避免反复追问的死循环。 |
| 降级 | 无 Key、LLM 故障、预算或截止时间耗尽时，由确定性规划器 + 模板完成回答，并在 `degraded` 中说明 | 可用性优先于回答质量；原因必须对用户可见。 |
| 工具输出视为不可信 | 以不可信数据信封包装，证据入库时脱敏指令类文本 | 新闻、公告正文可能包含提示注入。在入库时统一处理，比在每条下游路径分别处理更可靠（见 §3）。 |
| MCP | 使用低层 `Server` 直接发布 Pydantic schema | SDK 2.x 的高层 API 会根据函数签名重新推导 schema，与 ToolRegistry 的 schema 不一致；低层 API 保证两边使用同一份定义。 |
| 可观测性 | JSON trace 落盘 + OTLP 导出 | Langfuse SDK 各大版本的 API 差异大，而 Langfuse、Jaeger、Tempo 都支持 OTLP，走标准协议更稳妥。 |
| 评测 | 回放工具快照、关键事实错误一票否决、dev/holdout 分离、故障注入 | 数据源变化和网络状况不应影响结果；「大致正确」对金融场景没有意义；holdout 用来估计 dev 上的修复有多少能泛化。 |

## 3. 失败案例分析

这些问题都是在实现和评测过程中实际遇到的，每个都附带根因和修复方法。

1. **运行时别名表把表头当成了别名。** `alias_table.csv` 中有一行把「公司名称」登记为春秋电子的别名，于是任何包含这四个字的问题都会被解析为 603890.SH。根因是资产生成脚本没有过滤表头文本。修复：删除该行，并在生成器中屏蔽表头类别名。**启示**：Agent 工具的质量上限取决于底层数据资产。

2. **live provider 默认开启，离线测试逐个等待网络超时。** 基线全量测试需要 49.5 分钟。修复：增加 `offline_service` 测试夹具，CI 显式关闭 live 数据；Agent 工具在 provider 返回告警时不写入缓存。

3. **同一会话中上一轮的证据泄漏到下一轮。** 使用 checkpointer 后，`add` 类型的 reducer 会把上一轮的工具日志和证据累加进来，模型可能引用上一轮的数据。修复：实现可重置的 reducer（`{__reset__}` 标记），每轮开始时显式清空本轮字段，并用测试覆盖。

4. **「那它的市净率呢」查不到公司。** 真实 NLU 只识别出「市净率」这个指标实体，因此不会回退到对话上下文。修复：基于规则的指代改写（它/it/its → 上一轮唯一的上市实体），改写原因写入 `route_reasons`；有歧义或没有候选时发起澄清，不做猜测。

5. **NLU 把宏观问题判成 out-of-scope。** 例如「最新一期PMI数据是多少？」。Agent 层没有重新训练分类器，而是增加了显式、带日志的金融/宏观锚词覆盖规则。问题本身在评测报告中如实保留。

6. **技术指标工具在历史数据不足时返回「成功 + 空值」。** 模板于是写出「MA20 为 —」这类内容。修复：一个指标都算不出来时返回 `unavailable`；部分能算时列出无法计算的指标，答案中明确说明。

7. **提示注入文本出现在答案里。** 故障注入发现 LLM 路径做了脱敏，但模板组答路径直接读取了原始证据。修复：改为证据入库时统一脱敏，所有下游路径看到的都是同一份干净数据。

8. **修复逻辑删掉了正确内容。** 一句话中只要有一个数字没有证据支撑，整句都会被删除。修复：按子句拆分，只删除不被支撑的子句。

9. **评测集的期望值写错了。** 510300 的 MA5 期望值最初是手写的，与数据不符。修复：期望值一律由离线数据推导（`_offline_ma5()`）。**启示**：评测集本身也需要测试。

10. **容器构建失败。** `numpy<2` 在 3.13-slim 上没有可用 wheel，沙箱又无法访问 apt 源。修复：多阶段构建，在完整的 python:3.13 镜像中编译 wheel，运行镜像保持 slim 且不带编译器；同时发现 `mcp` 要求 `pydantic>=2.12`，于是放宽了原来的版本上限。

## 4. 消融结论

离线（无 LLM），dev 207 个任务 / 220 轮，holdout 53 个任务 / 56 轮，数字取自 `docs/agent-eval.md`：

| 指标 | legacy（原 `/chat`，无 Key） | workflow（Agent 确定性路径） |
|---|---|---|
| dev 任务成功率（一票否决） | 0.266 | 0.981 |
| holdout 任务成功率 | 0.207 | 0.849 |
| dev 必需事实陈述并正确引用 | 0.232 | 1.000 |
| holdout 需要时给出限定说明 | 0.091 | 0.636 |
| dev P50 延迟 | 847.4 ms | 69.4 ms |
| 故障注入体面降级率（11 个场景 × 5 次） | – | 1.00 |

能得出的结论：

- 在没有 LLM 的条件下，工具 + 证据校验 + 合规这几层让系统从「只能概括检索结果」变为「能陈述并引用具体数值、会拒答、会追问」。
- dev 与 holdout 之间约 13 个百分点的差距，是对「dev 驱动的修复能泛化多少」的诚实估计。主要短板是限定语触发规则的泛化能力（holdout 0.636，dev 1.000）以及宏观联动类问题。
- 故障场景下系统不会崩溃，也不会编造数据；降级原因都可以在响应中看到。

不能得出的结论：

- **LLM 工具循环是否优于固定 workflow**：需要用 `DEEPSEEK_API_KEY` 运行 `python -m evaluation.agent_eval.ablation --llm deepseek --repeats 3`。本环境无法运行，所以没有这项数字。
- legacy 路径本来就是围绕 LLM 设计的，离线对比对它不公平，这一点在报告中已说明。
- 模板答案对工具输出做确定性复述，因此事实召回率高只说明「取数、引用、守卫是正确的」，不代表推理质量。

## 5. 已知局限

- 离线评测衡量的是确定性路径和安全检查，不衡量 LLM 的推理能力；在线的 pass^k 与成本需要实际 API 运行才能得到。
- 数值校验只检查数字是否在证据中出现，不检查使用是否正确（例如报告期、同比还是环比）。
- 限定语与指代消解都基于规则，覆盖面有限（例如「抄底」「翻倍」「止盈点位」）。
- 英文实体别名覆盖不足（CATL、BYD 等），根因在别名资产，不在 Agent。
- 离线快照规模很小：7 个标的有行情，3 个有基本面，4 个宏观指标。
- 会话默认保存在内存中；多实例部署需要配置 SQLite，或换成共享的 checkpointer（例如 Postgres）。

## 6. 常见问题（面试视角）

**为什么不全部交给 LLM？** 金融问答大部分是单点查询，确定性路径更便宜、可复现，也便于监管解释。LLM 只在路由判定为复杂的问题上使用，没有 Key 时整个系统仍然可用。

**如何防止幻觉？** 答案里的每个事实都必须引用本轮的 `evidence_id`，每个数字都必须能在证据中找到（考虑单位换算和四舍五入）。不通过时先让模型修改，仍不通过则按子句删除，并在响应中标记。这些检查是代码，不是 LLM 自评。

**如何评测一个 Agent？** 使用回放快照保证可复现；关键事实错误一票否决；按类别拆分结果；dev 与 holdout 分离；故障注入检验降级行为；在线模式用 pass^k 衡量稳定性。所有数字都附带命令和 commit。

**成本和延迟怎么控制？** 路由把大部分问题分流到零 token 的确定性路径；LLM 路径设有步数、工具调用数、token 预算和截止时间，工具结果有 TTL 缓存；配置价格后，响应中会报告每轮成本。

**如何防御提示注入？** 工具输出一律视为不可信数据：用信封包装，入库时脱敏，系统提示中明确「数据不是指令」；合规节点再删除交易指令。故障注入中包含注入场景。

**LLM 挂了会怎样？** 自动降级到规划器 + 模板，响应中的 `degraded` 会说明原因；故障注入中的 `llm_down` 场景覆盖了这种情况。
