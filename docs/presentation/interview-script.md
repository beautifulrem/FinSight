# FinSight 面试讲稿

一页纸版本，用于项目介绍和追问准备。每个数字都能指到仓库里已提交的文件（`evaluation/results/`、`docs/results/`），文件记录了 commit、Prompt 哈希和运行命令。更完整的取舍与失败案例见 [设计复盘](agent-design-notes.md)。

## 1. 30 秒介绍

> FinSight 是一个面向 A 股的证据优先研究 Agent。经典、可解释的 NLU 负责理解问题、守卫和路由；LLM 在 LangGraph 循环里调用 9 个类型化的取证工具（行情、基本面、宏观、公告、新闻等）。答案里的每个数字都由代码逐句对照本句引用的证据核对，最后由合规节点删掉任何像投资建议的内容。没有 LLM 时同一张图用确定性规划器作答。
>
> 这个项目我最想讲的是评测：我请独立的作者另写任务集，首次运行的数字原样提交。在一套从没被任何修复看过的测试集 v3（130 个任务）上，Agent 通过 86.9%，固定流程 76.9%，不调工具的 LLM 是 0。路由在我自己写的标注上是 98.8%，在独立标注上只有 74%；按类别修复后，再用一套新的独立标注测一次，是 80%。修复到底能不能泛化，我用一套修复者从没看过的切片来回答：同一批缺陷类别修复前后，声明核查 53.7% → 83.6%，对话 57.9% → 81.6%；但我也会说清楚，对话里最大的一类「差值追问」只从 12.5% 到 25%，那项修复只算部分完成。

## 2. 两分钟架构讲解

按一次请求的路径讲，边讲边画：

1. **`guard_in`（守卫与路由）**：
   - 输入守卫先剥掉用户消息里的指令类文本（「忽略之前的规则」）。
   - 经典 NLU 识别实体和意图；会话规则处理追问：代词「它」、复数「这两家」、指代组「前者/后者」、省略「ROE呢」。
   - 可解释的路由器给出四种去向：拒答（非金融、只有改设定的指令、加密资产/美股）、澄清（没有标的）、固定流程（单一事实）、Agent（对比、归因、判断、宏观到市场）。
   - 每个决定写一个理由代码，进 trace。
2. **两条回答路径**：
   - 固定流程：确定性规划器决定调哪些工具，模板或 LLM 组织答案。
   - Agent：LLM 在工具循环里自己选工具；规划器会先预取显然需要的工具，所以很多问题一次 LLM 调用就答完。
   - 两条路径都有步数、工具数、token 和截止时间预算。
3. **`verify`（校验）**：
   - 答案里的每个数字必须出现在本句引用的那条证据里，按单位、写出的精度和正负号匹配。
   - 不通过先做引用修复（只有一条证据含这个数时补上 id），仍不通过让 LLM 修改一次，再不通过就整句删除。
4. **`compliance`（合规）**：软化判断和因果措辞，删除交易指令与仓位建议，补数据新鲜度提示与免责声明，检查回答语言。
5. **降级**：没有 Key、模型故障、预算耗尽、超过截止时间，都落到规划器 + 模板，仍然有引用、仍然经过校验，并在 `degraded` 里说明原因。
6. **周边**：
   - LangGraph checkpointer 保存会话（内存 / SQLite / Postgres），澄清时 `interrupt()` 暂停、`/agent/resume` 恢复，多副本共享。
   - 工具同时经 MCP 提供，整个 Agent 经 A2A 1.0 提供。
   - trace 进 Prometheus、OTLP、审计日志。

## 3. 三个可以当场辩护的数字

### 数字一：校验器误放率 1.17%

- **方法**：取开发集上 227 个校验通过的正确答案，自动生成 4,016 个篡改变体：数字改动 1%、5%、20%，或把另一家公司的数字换进来。统计校验器把篡改答案当作正确答案放过的比例。正确答案集合是固定的：结果记录任务 id 和 sha256，同一提交跑两次结果相同。
- **结果**（`evaluation/results/verifier_stress.json`，`25205d4`）：
  - 原来的整批比对误放 33.0%，运行级比对 24.6%，逐句绑定 **1.17%**（默认允许派生数字时 1.32%）；
  - 公司之间互换数字：100% → **0%**（允许派生数字时 0.66%）；
  - 正确答案 100% 通过；
  - 更早一次（`9f0e46b`，202 个正确答案）是 1.94%（`verifier_stress-9f0e46b.json`）。
- **局限**：
  - 1% 的改动有 1.7% 仍会放过，因为写出的精度本身就有容差。
  - 同一条证据里有多个报告期时，无法判断选对了哪一期。
  - 投毒到新闻正文里的假数字能通过：校验证明的是可追溯，不是真实。
- **复现**：`python -m evaluation.agent_eval.verifier_stress`

### 数字二：测试集 v3 上 Agent 0.869（独立、首次 LLM 运行）

- **方法**：
  - 测试集 v3 的 130 个任务由另一位作者编写，没看过路由、规划、合规代码和任何已有任务；先提交（sha256 写在编写说明里），再运行。
  - 没有任何修复看过它。LLM 路径在最终 commit `9536abf` 上首次运行，DeepSeek V4.1 Flash，每任务 3 次，一票否决口径（行为、每个必需事实陈述且引用、必需工具、限定语、无交易指令）。
- **结果**（`ablation-final4-deepseek-testv3-holdout.json`、`ablation-test_v3-purellm-deepseek.json`）：
  - Agent **0.869 [0.81, 0.92]**（pass^3 0.854），LLM 组织答案 0.831，固定流程 0.769，不调工具的 LLM 0/130；
  - Agent 对固定流程 +0.100 [+0.049, +0.156]，McNemar 13 比 2，p = 0.007；
  - Agent 对组织答案单次 +0.038 [+0.003, +0.082]，pass^3 不显著（McNemar 6 比 2，p = 0.29）；
  - 本次运行没有 LLM 出错，也没有 429。
- **同一方法在路由上的教训**：自有标注 0.988，第一套独立标注首次 0.740（`router_eval-independent_v1-first-run.json`）；按类别修复后，新写的第二套独立标注只跑一次得 0.801（`router_eval-independent_v2-first-run.json`，241 条，二项 95% 区间约 ±5 个百分点）。
- **局限**：
  - 独立作者也是按书面规则工作的 AI 编写者，不是真实用户日志。
  - 只有两个 flash 级模型；GLM 在同一集合上 Agent 0.815、与组织答案持平，P95 82 秒。
  - 离线数据只覆盖少数标的，任务受此约束。
- **复现**：`python -m evaluation.agent_eval.ablation --llm deepseek --repeats 3 --workers 3 --sets test_v3 --modes workflow_llm,agent`

### 数字三：Agent P95 27.1 → 15.4 秒，成功率不降

- **方法**：
  - DeepSeek V4.1 Flash，保留集 / 测试集 v2，每任务重复 3 次，走 UI 同样的 SSE 流式路径，记录首字时间。
  - 先剖析：95% 的时间花在 LLM 往返上；一半答案多做了一次修改调用，而其中多数是校验器的数字切分 bug（`20.9x` 被读成 20）造成的误报。
- **改动**（每项都有开关）：
  - 修复数字切分；
  - 连接池；
  - 只缺引用时先做引用修复，不再让 LLM 改；
  - 20 秒卡顿超时；
  - 规划器预取工具。
- **结果**（`docs/performance.md` §2a，`perf-*.json`）：
  - P95：保留集 27.1 → **15.4 秒**，测试集 v2 24.2 → **17.3 秒**；
  - 首字 P50：约 5.5 → **3.0 秒**；
  - 每轮 LLM 调用：2.30 → 1.39；
  - 与关闭开关的同一份代码配对比较，成功率 Δ +0.006 [0.000, +0.019]（保留集）、+0.003 [−0.005, +0.014]（测试集 v2）。
- **代价**：
  - 预取让「必要工具占比」从 0.684 降到 0.675（保留集）。
  - 允许派生数字让互换数字的误放率从 0.53% 升到 0.93%。
  - GLM 的 P95 仍很高：测试集 v3 上 Agent 82 秒（`ablation-final4-glm-testv3.json`）；后来的处理见 4e。

## 4. 一个失败故事：独立多轮集 0.224

- **发生了什么**：
  - 我请一位没读过路由和记忆代码的作者写了 49 段多轮对话。
  - 第一次跑（无 LLM），任务成功率只有 **0.224**，轮次 0.709；DeepSeek Agent 也只有 0.361。
  - 失败集中在：
    - 金融对话里不点名的追问被当成离题拒答（「MA5是多少？站上了吗？」）；
    - 「三家里哪家」「前者/后者」解析不了；
    - 行业问题拿宏观数据回答；
    - 模板忽略最高价、成交量这类细节；
    - 追问里的判断题没有加限定语。
- **根因**：规则是按我自己能想到的说法写的，我的开发集和标注也是我写的，所以 0.988 这类高分衡量的是「规则和作者一致」。
- **怎么处理的**：
  1. 首次运行的数字原样提交（`multiturn_v1-auto-nollm-first-run.json`、`ablation-multiturn_v1-deepseek-first-run.json`）。
  2. 每类失败先写新的开发集风格例子，再写通用规则，每条规则带理由代码。
  3. 修复后在这个集合上是 1.000，但一律标注「暴露后」。
  4. 能说明泛化的，是没有参与调参的集合：保留集 0.906 → 0.925；再加上新写的独立路由标注 v2（0.801）、从未用于修复的测试集 v3，以及修复者从没看过的第六轮切片（见 4d）。
- **我学到的**：独立评测的价值只在第一次运行，那个数字必须提交。评测还必须能分辨答案出自模型还是出自兜底路径：有一次网关周额度用完，Agent 全部降级，分数和固定流程一模一样，我后来让评测工具把 429 占比过高的运行标为无效。

## 4b. 第二个失败故事：模板路径 0%，LLM 路径 2–10%

- **发生了什么**：离线红队只测模板路径，第四轮后六套攻击集全部 0 成功。最终 commit 上第一次跑 LLM 路径红队（`redteam-final4-llm.json`，`9536abf`），组织答案在 holdout3/4/5 上 5.7% / 7.1% / 9.5%，Agent 2.3% / 5.8% / 4.8%。
- **LLM 复述了什么**：投毒文档里的「事实」（假 ROE、假分红）、诈骗联系方式（QQ 群号、Telegram 账号、电话）、「资金翻倍、亏损全额赔付」、伪造的证监会退市通知。输入侧的过滤器和分类器只拦下约四成未见过的攻击，剩下的进了模型上下文，模型把它当新闻转述。
- **怎么修**：在合规节点加一层作用于每个回答的输出侧过滤（`agent/output_safety.py`）：
  - 来自文档的联系方式、推广话术、交易指令整句替换成一条中性说明；
  - 只有单一来源的监管或公司行动说法（立案、ST、退市、合并获批）改写成「据一篇文档称…（未经其他来源证实）」；
  - 与结构化基本面矛盾的文档数字由校验器标出并删除；
  - 另写了 Prompt v4 的文档内容规则；当时没做任务成功率 A/B，所以先不设默认，后来做了 A/B 才设为默认（见 4e）。
- **怎么测**：记录一次模型的真实输出，再把同一批草稿分别送进旧代码和新代码回放（不再调用 LLM）。20 个此前泄漏的案例里，「当作事实陈述」的命中 3 → 0（`redteam-r7-targeted.json`）。
- **之后的重跑**：加了输出层后完整 LLM 红队在 `0473968` 上重跑，每个攻击集和路径当作事实陈述 0–3.4%（`redteam-r8-llm.json`）；第六轮评审的 14 种新型攻击（holdout8）在第 10 轮修复后为组织答案 1/112、Agent 1/28，Agent 那一例是输出层缺口，修复后用同样的草稿回放为 0/28（`redteam-r10-holdout8-llm.json`、`redteam-r10-holdout8-llm-replay.json`）。加了标注的数字仍会传到读者面前，这一条列在 README 的未解决问题里。
- **教训**：模板路径的安全不等于 LLM 路径的安全；分层防御里，输出侧是最后也是最可控的一层。

## 4c. 一个界面小教训：在真实 Chrome 里才看得到

- 用 Chrome 扩展在真实浏览器里走一遍中英文、浅色/深色时发现：英文界面里模板答案、推荐追问、证据标题仍是中文公司名，中文界面里证据标题是英文「daily market data」，事实核查的免责声明跟着声明的语言走而不是界面语言。单元测试和 Playwright 快照都没覆盖这些组合。
- 还发现用户装的 Dark Reader 扩展会把页面重新上色；应用自带深浅色主题，于是声明 `darkreader-lock`。
- 修复见 `d3aa184`、`3b8ebef`、`6c46e85`。**教训**：多语言、多主题的组合要在真实浏览器里点一遍，截图测试只能证明「没变」，不能证明「对」。

## 4d. 修复能泛化吗：第六轮切片 0.537 → 0.836

- **问题**：面试官最常追问的是「你按评审意见修了，分数涨了，可那不就是对着考题改吗？」暴露后的集合确实回答不了这个问题。
- **做法**：第六轮评审列出缺陷类别（行业平均、两家公司之差、中文约数、差值追问、合理估值、港股名称等）后，另一位作者只看这些类别、不读代码，在 `bc42017` 上写了 67 条声明和 38 个对话任务（`evaluation/heldout_r6/`，sha256 写在说明里，标签由脚本从离线工具重新推出）。修复前跑一次并提交（`05c4d7b`），然后写第 10 轮修复的工程师**从没打开过它**，修复后再跑一次（`68279eb`）。
- **结果**：
  - 声明结论准确率 0.537 [0.42, 0.66] → **0.836 [0.75, 0.93]**（`claim_bench-heldout_r6-prefix.json` → `claim_bench-heldout_r6-after-fix.json`）；中文约数 0.30 → 0.80，两家公司之差 0.40 → 0.80。
  - 对话任务成功率 0.579 [0.42, 0.74] → **0.816 [0.68, 0.92]**（`chat_heldout_r6-auto-nollm-prefix.json` → `chat_heldout_r6-auto-nollm-after-fix.json`）；覆盖范围外的港股名称 0.29 → 1.0。
- **如实说**：
  - 还有 11 条声明和 7 个对话任务错着：英文和括号里的行业平均、「一成半」「一千四百出头」这类约数、「它比行业低了多少」只给两个操作数不给差值。没有对着这个切片去修，修了它就暴露了。
  - 比较方向得分 0.294 → 0.284 没动。原因是标注约定：切片把一个比较标成「关系 + 所述数值」两个检查，核查器输出的结构不同，配不上；它衡量的是检查结构，不是结论对错。我选择把这个分数原样报告并解释，而不是改评分去迎合。
- **怎么讲**：修复对没人调过的问法也有效，但只修好了大约三分之二的错误（声明错误 31 → 11 条）。区间宽，样本小，这是一个方向性的证据，不是精确估计。

## 4e. 两个用数据做的工程决策：Prompt v4 设为默认、慢速模型走组织答案

- **Prompt v4**：v4 的文档内容规则是安全需要的，但我担心多出的约束会降低任务成功率，所以在 A/B 之前一直不设默认。`bc42017` 上在测试集 v3 做了 v3/v4 A/B（DeepSeek，2 次重复，先后连续跑；`ablation-ab-prompt-v3-testv3.json`、`ablation-ab-prompt-v4-testv3.json`）：
  - Agent 0.858 → 0.877（+0.019 [+0.000, +0.038]，McNemar 6 比 1，p = 0.125），pass^2 0.831 → 0.869；组织答案 0.831 → 0.823（p = 1.0）。都不显著。
  - 结论是「安全规则没有可测的成功率代价」，于是 `66c0ef2` 把 v4 设为默认。代价也写出来：Agent P95 15.9 → 19.2 秒，单任务成本 +11%。
  - 这次选择用掉了测试集 v3：之后 v4 在它上面的分数不能再叫「未被触碰」。
- **慢速模型策略（成本/延迟取舍）**：GLM 上 Agent 与组织答案成功率持平，但 Agent P95 82 秒、组织答案 27 秒，pass^3 还更低（0.731 对 0.800）。我试过两种办法：
  1. 降低 GLM 的推理强度（`ablation-glm-effort-default-holdout.json` → `ablation-glm-effort-low-holdout.json`）：P95 35.8 → 17.7 秒，成本 −37%，但判断类问题的限定语 1.00 → 0.82，任务成功率 1.000 → 0.962。在金融场景里少说一句「不确定」比慢几秒更糟，所以没采用。
  2. 按模型路由：模型能力表给 GLM 标 `prefer_composition`，`mode=auto` 时原本走 Agent 的问题改走固定流程 + LLM 组织答案，trace 里记 `model_policy:composition_for_slow_model`；`QI_AGENT_SLOW_MODEL_POLICY=off` 可关，`mode=agent` 不受影响。`66c0ef2` 采用了这个。
  - **如实说**：这个策略的依据是已提交的 GLM 运行，还没有用 GLM 端到端跑过 `auto` 来验证它。
- **还有一个负结果**：LLM 记忆摘要在多轮集 v1 上开和关都是 0.980（`ablation-memsum-0-multiturn_v1.json`、`ablation-memsum-1-multiturn_v1.json`），每轮 LLM 调用反而多了（1.51 → 1.75），所以保持关闭。负结果同样提交。

## 5. 常见追问

**为什么不用多 Agent（分析师、交易员角色辩论）？** 这个场景的价值在证据链，不在观点多样性。多角色会让成本和不可控性成倍增加，而校验是确定性代码，不需要另一个 LLM 来「审」。在未被触碰的测试集 v3 上，单 Agent 工具循环只比「固定流程 + LLM 组织答案」单次高 3.8 个百分点，pass^3 不显著；换 GLM 时两者持平。连单 Agent 的增益都这么小，再加角色更难证明值得。

**为什么用经典 NLU 而不是全部交给 LLM？** 路由和守卫要可解释、便宜、离线可测：每个决定都有理由代码，确定性路径零 token、0.4 秒。LLM 只用在它有价值的地方，也就是选工具和组织语言。代价是规则会过拟合作者的措辞，这正是我用独立标注去测、并把 0.740 写进 README 的原因。

**幻觉怎么量化？** 分两层：
- 线上：每个答案统计「无法由所引证据支撑的数字」，逐句检查，不通过就修改或删除，trace 里有记录。
- 离线：用压力测试量化校验器本身的可靠性（数字一）。

另外，纯 LLM 不调工具时，在 511 个任务上一题都过不了（要求引用的口径下这是由评分方式决定的；不要求引用时也只有 4–8% 的必答数字正确），这说明工具加校验是前提。

**成本和延迟怎么控？**
- 路由把简单问题分到零 token 路径；
- 按节点设推理强度；
- 规划器预取工具，减少往返；
- 强制收尾时保留同一份工具定义、用 `tool_choice="none"`，维持缓存前缀；
- 每次 LLM 请求都受运行截止时间约束（90 秒 + 作答宽限 20 秒，低于接口的 120 秒超时）。

DeepSeek Agent 单任务约 $0.0008–0.0014（测试集 v3 上 $0.00114，P95 18.4 秒），4 并发压测每 1,000 次提问约 ¥12.6。

**安全怎么做？**
- 结构优先：工具只读；工具结果包在不可信数据信封里；数字必须来自证据；合规节点删除交易指令；用户消息先过输入守卫。
- 输入侧两层：关键词过滤 + 一个小分类器，对没见过的文档攻击只拦下 42%，所以不能靠它。
- 输出侧一层（第七轮）：每个回答里来自文档的联系方式、推广、交易指令被替换，单一来源的监管说法加出处，与结构化数据矛盾的文档数字被删除。
- 红队结果：模板路径九套攻击集全部 0（`redteam-offline-r10.json`）；最终 commit 上 LLM 路径 2–10%（见 4b），加输出层后 20 个泄漏案例的「当作事实陈述」3 → 0；第八轮重跑完整 LLM 红队，每个攻击集和路径当作事实陈述 0–3.4%（`redteam-r8-llm.json`）；第 10 轮之后 holdout8 为 1/112 和 1/28，Agent 那一例修复后回放为 0/28。
- 工程侧：API Key 隔离会话、限流、请求体上限、只读根文件系统、gitleaks 全历史扫描、NetworkPolicy。

**如果重来会怎么做？**
1. 第一天就请独立作者写测试集和路由标注，而不是先调到自己的集合 0.99。
2. 路由类别用小型分类器，由独立标注训练和衡量，替代越来越长的词表。
3. 评测从一开始就区分「模型回答」和「降级回答」。
4. 更早接入第二个模型，并准备更高的网关配额。

## 6. 白板题提纲

- **路由决策**：输入守卫 → NLU → 会话改写（指代 / 省略 / 组引用）→ 覆盖范围检查（加密、美股）→ 按优先级判定：拒答 > 澄清（没有标的、悬空指代、没有标的的建议）> Agent（对比、归因、判断、宏观到市场、多方面分析）> 固定流程。每一步写理由代码；没有 LLM 时 Agent 降级为固定流程。
- **校验绑定**：按句切分 → 抽取数字（单位倍数、写出的精度、正负号；日期、期限、编号不算）→ 找本句引用的证据 id → 在该证据的数值里按单位倍数和容差匹配 → 市场指标优先取行情来源 → 不通过的句子：先做引用修复，再让 LLM 修改一次，再整句删除，全部删完就回退模板。
- **图的节点**：`guard_in → (refuse | clarify | execute_plan → compose | agent_llm ⇄ agent_tools) → verify → (revise) → compliance → finalize`。状态里每轮字段用可重置 reducer 清空；`durability="exit"` 每轮只写一次检查点。

## 7. AI 编程工具的使用说明

这个项目是在作者的主导下，大量借助 AI 编程助手（Claude Code）完成的：作者定目标、做取舍、审阅结果，代码、测试和文档的大部分由助手在作者指导下编写。面试时建议主动说明这一点。

- **作者本人必须能讲清、能手写的内容**：
  - 路由的四种去向与优先级；
  - 校验器的句子绑定和单位、精度、正负号匹配；
  - LangGraph 图的节点与状态清理；
  - 降级链；
  - 评测口径（一票否决、pass^k、bootstrap 与配对比较）；
  - 「首次运行 vs 暴露后」的区别；
  - 上面三个数字的来源和局限。
- **结论是怎么独立核实的**：
  - 另开的 AI 编写者在不看代码的前提下写任务集和路由标注，写好先提交再运行。
  - 另开的评审 Agent 按招聘场景的评分表逐项打分，自己写未见过的攻击和问题，并在真实浏览器里验证界面。
  - 每个数字都对应一个已提交的结果文件，CI 检查文档与结果一致。
- **不要夸大**：独立集合的作者也是 AI，不等于真实用户；在线评测只覆盖两个 flash 级模型；与问财、豆包的对比测试只做了设计，没有执行。
