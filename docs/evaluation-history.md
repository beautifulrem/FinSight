- **Rounds 6 and 7**: the slices were committed to the repository with their first run (`05c4d7b`, `12a28eb`) before
  the fix rounds started, and the after-fix runs read them from there. That the engineers did not open them is their
  statement.
- **Rounds 8, 9 and 10**: each after-fix run read the slice from the reviewer's folder outside the repository (its
  `config.tasks_file` is `/Volumes/Remi/finsight-review/heldout_rN/...`), and the slice was committed only afterwards.
  For example, the round-10 after-fix run is at 18:07:35Z at `3480a96`, and the commit `367636b` follows at 18:09:28Z.
  No fix-era commit names a slice item. Nothing records file access either, so "not opened" stays a statement, not a
  measurement ([round-10 provenance](../evaluation/heldout_r10/README.md#provenance-of-the-after-fix-run-what-the-record-shows-round-11-review-k16)).

## The long summary

The README's former "In 30 seconds" block, kept as written at `4ad3380`.

- **Numbers you can trace.** The claim-level verifier rejected 99.1% of 5,551 corrupted answers (98.9% with derived numbers allowed, the default) and accepted all 328 correct ones (`verifier_stress-round15.json`, run at the final round-15 code `8b62a6c` and committed in `67db0aa`, a pinned gold set whose task ids and sha256 are recorded; 5,452 / 324 at the merged round-14 code `aef319a`, 5,202 / 306 at the merged round-13 code). A number swapped in from another company passed 0 of 1,224 times (0.6% with derived numbers allowed); with the original check it passed 100% of the time. Answers that fail are repaired by deleting whole sentences: 100% readable, where the old clause salvage left 26% readable (`verifier_stress-clause-salvage.json`).
- **Measured on a set nobody tuned against.** On test v3 (130 tasks written by a separate author, first LLM run at the final commit `9536abf`), the DeepSeek agent passes **0.869 [0.81, 0.92]** of tasks, LLM composition 0.831, the deterministic workflow 0.769 and an LLM without tools 0 (strict, citation-gated scoring). The agent beats the workflow significantly (+0.100 [+0.049, +0.156], McNemar p = 0.007) and composition per run (+0.038 [+0.003, +0.082]), but not on pass^3. With GLM the agent is no better than composition (−0.003 [−0.044, +0.041]) and its P95 is 82 s.
- **Out of sample, after the fixes.** Each review's author writes a held-out slice from the bugs they found, before any fix; the engineers who fix those bug classes state that they never open it (round 15: [what this rests on](#provenance-of-the-reviewer-slices-round-15-note)), and it is run once before and once after. Round 6: claims **0.537 → 0.836**, chat **0.579 → 0.816**. Round 8 (the round-7 classes reworded by another reviewer): **0.275 → 0.686** after round 12 (claims 0.600 → 0.800; 32/48 without three turns that coincide with own wording, [provenance](../evaluation/heldout_r8/README.md#provenance-of-the-after-fix-run-round-13-check)). Round 9 (52 chat tasks and 25 claims on the snapshot extension's names: shares, verb comparatives, sums, spreads, several holdings, 52-week and YTD questions, forecasts): chat **0.346 → 0.788** (18/52 → 41/52), claims **0.600 → 1.000** after the round-13 fixes; 6 chat tasks and 5 claims overlap own wording (every task and claim file scanned), and without them chat goes 16/46 → 36/46 and claims 15/20 → 20/20 ([per class](#the-round-9-slice-per-class)); sums (1 of 5) and price-derived questions (2 of 7) stayed weak. Round 13 read the round-8 slice and round 14 the round-9 slice (44/52 before reading it, 51/52 after), so their later numbers are **after exposure**.
- **Every independent set is reported twice: first run, then after exposure.** Separate authors wrote a multi-turn set, test v3, two router label sets and three round-4 held-out slices without seeing the code. First runs: multi-turn 0.224 (no LLM) / 0.361 (agent), router labels 0.740, round-4 claims 0.716, round-4 multi-turn 0.667, planted-document attacks 0/168 on the template path. - **Honest statistics.** Every rate has a 95% bootstrap CI, and paths are compared with paired bootstrap + exact McNemar. On held-out the agent (1.000) is not significantly better than composition (0.981); after the round-8 output-layer fixes the LLM paths still state 0–3.4% of planted-document payloads as fact (2.8–6.8% raw detector hits) where the template path lets none through (see [Known open issues](known-issues.md#known-open-issues)).
- **Runs like a service.**
  - It works without an LLM, and every LLM call is bounded by the run deadline.
  - The DeepSeek agent's P95 is 15–17 s, and the first answer token arrives after about 3 s.
  - It has been load- and chaos-tested (8 users without an LLM while the chaos drill blocks the market sources: 0 errors in 400 requests, [performance.md §1b](performance.md#1b-workflow-path-under-the-source-chaos-drill-no-llm-8-users); 8 users on the LLM `auto` path: 0 errors in 24 requests, P95 24.3 s, 0 × 429, `r13-load-8u-auto.json`), and runs on k3s with Postgres-shared sessions, tasks and traces.
  - It exposes MCP (server and client) and A2A, and ships Prometheus/Grafana/Jaeger monitoring.
- **Why not just use 豆包 / 问财?** [docs/comparison.md](comparison.md) covers what they do better, what none of them publishes, and a fair head-to-head test (designed, not run).

## Results

Strict ("dealbreaker") scoring: a task succeeds only if every one of these holds:

- the behaviour is right (answer, clarify or refuse);
- every required fact is stated **and** cited;
- the required tools were used;
- a judgment question gets hedged;
- no trading instruction appears anywhere.

Online runs use 3 repeats per task, and costs are as billed by the gateway. Each number below comes from a committed file in [`evaluation/results/`](../evaluation/results/), which records the commit, the prompt hashes and the command of its run; since round 12 also the `QI_*` switches and model id in effect (`config.env`, `config.command_with_env`; credential- and URL-shaped names are never recorded). Per-category tables and every paired comparison are in [docs/agent-eval.md](agent-eval.md). A Chinese summary is in [docs/zh/evaluation.md](zh/evaluation.md).

## Limits in full

- **Two model families, both flash-class, both through one gateway.** The final online run is at `9536abf`; the round-7/8 output layer and later UI fixes came after it (they do not change offline task success; the LLM-path red team was re-run after them at `0473968`).
- **Few unexposed task sets.** Test v3 has never been used for a fix, but it chose the default prompt at `bc42017`. Each reviewer slice is out of sample for exactly one round of fixes: round 6 (claims 0.836, chat 0.816 after round 10), round 7 (chat 0.830 after round 11), round 8 (chat 0.686, claims 0.800 after round 12), round 9 (chat 0.788, claims 1.000 after round 13, with 6 chat tasks and 5 claims overlapping own wording) and round 10 (chat 0.792, claims 0.833 after round 14, with 3 chat tasks overlapping by text; 6 tasks and 5 claims with the round-15 content-level scan). They are small (24–67 claims, 38–53 chat tasks), and every later run on them is after exposure: the round-9 slice from round 14 (51/52 after the round-14 engineer read its failures), the round-10 slice from round 15. Held-out chose prompts; test v2, multi-turn v1, router labels v1 and the round-4 and round-5 slices are after exposure.
- **Routing still misses about one question in five on fresh phrasing.** The fresh independent router set scored 0.801 on its first run and 0.842 after exposure (clean rerun at `d42b181`; 0.8423 again at the round-14 code `dc2fcb0`). Advice with no target and borderline clarify-or-refuse cases are the main misses.
- **The agent loop is only slightly better than LLM composition.** On test v3 with DeepSeek it is ahead per run (+0.038) but not on pass^3; with GLM they are tied; the agent costs 1.1–4x as much.
- **The verifier proves traceability, not truth.** It checks that numbers come from the cited evidence. It cannot tell whether the right period or metric was chosen when one evidence item holds several. A fake price planted inside a news excerpt passes, because it *is* in the evidence.
- **Real-world claims: five engineer-collected sets, no owner set yet.** 60 claims quoted as published (37 media, 14 social posts, 5 broker notes, 4 company announcements; [evaluation/real_claims_web/](../evaluation/real_claims_web/README.md)) score 0.800 [0.70, 0.88] on their first run (`claims_web_v1-first-run.json`). The collector had read the checker, so the set is not blind. On the first run the offline data disagreed with the companies' own reports on 19 of the 60 claims, so those true published claims were labelled, and shown, as wrong or partly wrong. The causes were seed fundamentals for 五粮液 and 中国平安, period-end vs weighted ROE, and total vs attributable net-profit bases. Round 13 corrected the seed values from the annual reports and resolved the two disputed 2026-04-22 prices (the media were right). With the corrections on, the checker marks 6 of those 21 claims supported instead of 2, and the set scores 0.817 [0.72, 0.90] after exposure (`claims_web_v1-with-corrections.json`). 15 claims still differ by definition: 14 on extension companies, whose values keep Sina's period-end ROE, total-profit YoY and diluted EPS (now stated; since round 14 the checker reads a definition a claim names and does not compare it with another), and one on 茅台's 营业总收入 (the layer serves 营业收入). A second set of 50 claims ([evaluation/real_claims_web_v2/](../evaluation/real_claims_web_v2/README.md)) was collected **blind to the checker**: collected, labelled and committed before its code or tests were read, by search agents that were never shown an offline value. On its first run the checker scores **0.500 [0.36, 0.64]** (`claims_web_v2-first-run.json`). That is well below the first set's 0.800, though the two sets also differ in label rules and mix. 4 of its claims are true on every part by the company's report but cannot be fully supported from the offline data, because the extension keeps other definitions (total-profit YoY, period-end ROE). Round 14 read both sets' error lists and changed the checker, so both are **after exposure**: the second set scores 0.840 (it is no longer a blind number; the blind one is 0.500), the first 0.850 on seed data and 0.783 with the corrections layer, where six claims that name a definition the data does not serve are now unverifiable but labelled as checkable. The checker now reads named definitions and never compares a claim with a field of another definition. Two more blind sets followed in round 15: the third (round 2, [evaluation/real_claims_web_v3/](../evaluation/real_claims_web_v3/README.md)) scored **0.540 [0.40, 0.68]** on its first run with the round-14 checker and 0.900 after its six classes were fixed (after exposure); the fourth (r15-claims, [evaluation/real_claims_web_v4/](../evaluation/real_claims_web_v4/README.md)) scored **0.740 [0.62, 0.86]** on its first run with the round-15 K6 checker, before the third set's rules, and 0.780 after them. A fifth blind set (r16-claims, [evaluation/real_claims_web_v5/](../evaluation/real_claims_web_v5/README.md), with ten dated prices and market values) scored **0.680 [0.56, 0.80]** on its only blind run with the round-16 checker. The blind numbers are the first runs. Round 15 also changed two conventions that the earlier labels do not follow: a claim whose only unverifiable parts name another definition is `supported` (partly checked), and a daily figure with no date that does not fit the latest session is unverifiable. The owner's own real-claims set (`evaluation/human/real_claims/`) is still owner-blocked.
- **Injection defence is layered, and the LLM path still leaks.** The lexical filter and the classifier catch 42% of unseen document attacks; the template path lets none through; the LLM paths let 2–10% through at `9536abf`. After the round-7/8 output layer the full LLM red team (`0473968`) finds 0–3.4% stated as fact per set and path (2.8–6.8% raw detector hits on composition, up to 4.6% on the agent); the layer attributes or removes, it cannot stop the model from mentioning a payload.
- **Follow-up handling is rule-based.** Session rules resolve pronouns, plurals, group references and ellipsis, and every rewrite is logged. Their wording lists came from what their author and the exposed sets showed. English company aliases cover major names only.
- **Latency.** With DeepSeek the agent's P95 is 15.4 s on held-out and 17.3 s on test v2, and the first answer token arrives after about 3 s (P50). Planner prefetch, citation repair and a 20 s stall timeout brought it down from 22–27 s without a loss in task success ([performance.md](performance.md#2a-agent-path-latency-profile-changes-and-beforeafter)). On harder multi-tool questions at 4 concurrent users the P95 is 26.7 s. With GLM the agent's P95 is 82 s on test v3, driven by per-call variance; since `66c0ef2` `mode=auto` sends GLM's agent-route questions to composition (P95 27 s) instead. Every LLM request is capped by the run deadline (90 s + 20 s for the answer, below the API's 120 s timeout).
- **Free data sources throttle.** Eastmoney refused this machine's connections during the audits (again at HEAD on 2026-10-01: `push2`/`push2his` 0/22 calls through the proxy), and the fallbacks carried the load. With a Postgres checkpointer, A2A tasks and traces are shared by all replicas too; the rate limiter and the caches are still per replica.

## CI, the pre-push check and the human-evaluation kit

`--llm deepseek` selects the client, the OpenAI-compatible one configured by `DEEPSEEK_API_KEY` and `DEEPSEEK_BASE_URL`. It does not select the model. The model comes from `--model`, else `DEEPSEEK_MODEL`, else `deepseek.model` in `config/app_config.json`, so the GLM runs were started with `--llm deepseek` and `DEEPSEEK_MODEL=cline-pass/glm-5.3-flash`. Every result file records the model it actually called (`config.model`), the client (`llm_client`) and where the model came from (`model_source`).

CI runs the following:

- lint;
- a gitleaks secret scan of the full git history ([SECURITY.md](../SECURITY.md));
- the frontend checks: typecheck, lint, unit tests and a reproducible build;
- the full test suite, run once, with a Postgres service, including the axe accessibility tests (they fail rather than skip in CI), and branch-coverage floors: `query_intelligence/agent` 88% (measured 90.17%), `query_intelligence/api` 90% (92.13%), `answer_guards.py` 81% (83.74%), from [`coverage-ef07a7f.json`](results/coverage/coverage-ef07a7f.json). The 90.3% quoted earlier came from the agent test subset only;
- the evaluation gate against committed baselines (dev and held-out pinned to the v1 seed; `ext` with the extension on; `shipped` with the extension and the corrections layer on, as deployed), and a check that the evaluation page is up to date;
- the Docker build with a smoke test on a read-only root filesystem (waits for `/ready`, checks that it lists the three data layers and that the answers carry the corrected figures 茅台 P/E 21.44 and 五粮液 ROE（加权） 6.89% / 营业收入 405.29 亿元), plus a check that an unwritable state volume makes the container unready;
- a Kubernetes smoke test: the kustomization is applied to a throwaway kind cluster through [`deploy/k8s-smoke`](../deploy/k8s-smoke/smoke.sh), with NetworkPolicies enforced. It waits for `/ready`, then, from an admitted client pod, checks the data layers, gets one verified `/agent/chat` answer and asserts one corrected figure (五粮液 ROE（加权） 6.89%, 营业收入 405.29 亿元) ([local runs](results/k8s-smoke/));
- Kubernetes manifest validation (rendered kustomization, no committed Secret, commit-tagged image).
